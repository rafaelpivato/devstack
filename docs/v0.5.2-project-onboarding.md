# v0.5.2 Stage 2 — project workspaces and GitHub onboarding

**Scope:** unreleased feature on `integration/v052-control-plane`, implementing
the project foundation in [ADR-0001](adr/0001-multiple-projects-single-runtime.md).
No existing v0.5.1 server can adopt this new database/paths automatically.

## Managed layout

```text
/var/lib/devstack/
  control.sqlite3
  projects/
    <immutable-project-uuid>/
      repos/<name>/                # Original Git checkout: unchanged by import
      managed/project.toml         # Private app metadata snapshot
      managed/tasks.toml           # Private task snapshot (optional)
      managed/compose.yaml         # Private Compose snapshot (optional)
      baseline/<filename>          # Original import files for future reviewed sync
      secrets/                     # Never committed into the Git checkout
      logs/
```

All project identity is UUID-based; display names can change without relocating
files or renaming Compose ownership. No project is implicitly activated by a
create, import or selection operation.

## Import protocol

1. Validate the GitHub URL and create a new UUID-scoped `.pending-<uuid>`
   workspace. HTTPS public repositories require no GitHub SSH identity; private
   SSH clones reuse the dedicated GitHub identity.
2. Clone and resolve either one unambiguous `.devstack/project.toml` or the
   explicitly chosen GitHub tree path, including branches with slashes.
3. Validate bounded application and task manifests and snapshot managed files
   and their original baseline **outside the Git checkout**.
4. Atomically reserve the project and linked repository/application/task metadata
   in SQLite as **pending**. Pending projects are not discoverable through the
   normal registry API.
5. Rename the pending workspace to its immutable UUID path, then mark the
   project **ready**. If final publication is interrupted, the controller can
   verify and finalize an intact published workspace on restart.
6. Cleanup of unpublished staging is limited to the new pending UUID directory.
   Published workspaces are **never silently deleted** if DB finalization fails.

Git cloning and manifest copying do not execute Compose stacks, build images,
start commands or publish ports. Docker Compose configuration validation before
activation belongs in the future controller/Compose adapter.

## Tests and status

- Unit tests: `tests/test_v052_project_import.py` and the Stage 1 registry suite.
- Docker CI: two independent imports from the **real public GitHub Smoke Test**
  sample, then `docker compose config` against each managed Compose snapshot
  with the original source path as the relative build-context base.
- Full v2 HTTP project onboarding, runtime switching, supervised jobs, public
  ingress and systemd privilege separation **are not implemented yet**.
- Full [AC-01–AC-16](v0.5.2-acceptance-plan.md) remains release blocking.
  Never merge the unfinished integration branch to `main` or bump the
  stable package version.
