## Approved experience

1. Active project first: root lands on the one active project if any. No active project → explicit choose/activate flow; never autoactivate.
2. A persistent multi-project registry is secondary and inspectable. Selecting a project doesn't activate or switch it.
3. Hierarchical, back-oriented navigation. Project home → feature list → detail → logs/review as needed. No omnipresent jump-anywhere links.
4. Mobile-first with good desktop responsiveness; neutral dark theme with restrained accent, accessible labels/icons beyond color, compact layouts.
5. Work only with real v0.5.3 functionality. Existing APIs and security boundaries constrain screens; don't manufacture IDE, interactive terminal, PR editor, test-analytics, usage tracking, public API or GPT connection.
6. Keep a changeable shell, feature modules and reusable primitives. Screen layout/order/text can be refined PR by PR without rebuilding architecture.

**Safety checks:** Do not present inactive services as running, do not infer application URLs without the returned Tailscale binding, do not equate service logs with stream/PTY, do not show commits/PRs/diffs/CPU metrics/test-suite structure the API does not provide. `settings_replace` is collection-wide with no revision gate; do not implement a misleading isolated edit experience. Only web-visible output or URLs get client-side contextual copy.

## Architectural implementation checks before I1

- [ ] Validate packaging path: v0.5.3 installs from published git tag using Python packaging/venv; ensure built frontend ships with both wheel and tagged source, without requiring Node on the deployed host.
- [ ] Prove Flask serves SPA/deep routes without masking `/api/v2`, existing CSRF/health endpoints, or webhook boundaries.
- [ ] Choose the smallest maintained router/cache approach; establish one typed client, one error mapper, one polling policy.
- [ ] Define feature routes using immutable project UUID and entity IDs, with safe controller-verified active context.
- [ ] Decide staged replacement/rollback strategy for legacy templates; do not strand functions between old and new UI.
- [ ] Record approved mockup language as visual reference only; source capabilities take precedence.

## Required test matrix

- [ ] **Python unit** suite including Flask CSRF and exact-field IPC protocol.
- [ ] **Real Docker** two-project A→B→A; jobs/logs/volumes/webhooks isolated and generation-fenced.
- [ ] **Fresh Ubuntu** systemd/Unix web vs control vs trusted SSH operator permissions; CLI remains functional.
- [ ] **Frontend** build/typecheck, component/interaction tests, mobile browser navigation/deep-link/back tests, visible handling of no active/controller failure and multi-tab project selection.
- [ ] **Packaging/release** wheel contains correct static assets, installed source can serve them, update and rollback assets match release; release CI still triggers only on owner-merged `main`.
- [ ] **UX/accessibility** keyboard/focus, touch sizes, text/icon statuses not merely colors, narrow viewport logs, long strings, reconnect/loading/error/empty states.
- [ ] **Evidence** attach links to actual green checks on feature PR head and integration head; avoid claiming unperformed real-host checks passed.

## Branch and merge discipline

- Feature PRs target `integration/v060-ui`; assistant may squash-merge after green full gates. Update living tracker and issue with actual head, PR number and evidence.
- Do **not** merge into `main`, create version tags, publish releases, or modify `v0.5.3`. A draft integration→`main` final PR is reserved for owner review/merge.
- Version is provisional `0.6.x`; coherent scope and release notes dictate the published patch number.
- The older real-host issue #50 stays deferred unless a confirmed safety regression demands action.

## Deliberate post-v0.6 work

- Use the current UI for several weeks on real projects; note friction qualitatively.
- Only later decide whether limited **private** usage tracking adds value (not retroactive; no code, secrets, logs or invasive telemetry).
- Decide on a focused development console/interactive terminal only with evidence. Keep tentatively planned secure GPT read-only observability separate; no version lock or dependency.
