# DevStack v0.6.0 — R1 staged acceptance runbook

**Status: Release-candidate preparation. Not published, not approved for default UI cutover.** This guide is designed to distinguish actual iPhone/Ubuntu observations from automated GitHub Actions evidence. Owner review is required before the final integration → `main` PR is merged.

## Environment and preconditions

- The candidate is the versioned `0.6.0` branch contents in `integration/v060-ui`, including its checked-in React JS/CSS assets. No Node/npm runtime is installed on the host.
- Open the candidate **only on a trusted, disposable or staging Ubuntu installation**, accessible over its existing private Tailscale interface. Do not replace a working deployment with an untagged branch through the production updater: `scripts/updater.py` deliberately accepts only tagged published releases.
- Before mutations, preserve state and volume/backups. The web UI and SSH CLI still share the single authoritative controller; browser testing must never change the active project except via an explicitly reviewed runtime operation.
- An already published v0.5.3 server does **not** contain the v0.6 `/__v06` screens. Merely opening that URL on an unupgraded server will not work; the candidate must first be made available on a staging host. If no staging deployment exists, record device QA as **blocked**, not passed.

## 1. Read-only staging smoke

On the staging Ubuntu host, use local HTTP access, not a publicly forwarded admin port:

```sh
curl --fail --silent --show-error http://127.0.0.1:8765/healthz
curl --fail --silent --show-error http://127.0.0.1:8765/api/v2/runtime
curl --fail --silent --show-error -o /dev/null http://127.0.0.1:8765/__v06
curl --fail --silent --show-error -o /dev/null http://127.0.0.1:8765/__v06/projects/create
curl --fail --silent --show-error -o /dev/null http://127.0.0.1:8765/__v06/projects/import
```

Expected: controller healthy; one of the documented runtime phases, **not** an inferred inactive state; opt-in preview and deep links respond with HTML and versioned JS/CSS, no changes to registered project counts or job/transition history. Check that `/` still returns the older dashboard in this candidate.

CI independently tests an installed wheel, real Docker A→B→A, controller/web Unix-socket permissions and a full npm audit. A green run proves **none of the physical iPhone interactions below**.

## 2. Real iPhone Safari acceptance

Open `http://<private-tailnet-host>:8765/__v06` (or the HTTPS tailnet equivalent already configured on the host). Never expose TCP 8765 publicly. Record the device, iOS/Safari version, host candidate commit and date; screenshots are optional and must not expose credentials/log secrets.

- [ ] **Entry and selection:** inactive → chooser; active → active project home. Inspect another project without activating it; verify labels distinguish “active” and “viewing”.
- [ ] **Hierarchy and deep links:** navigate Project → Repositories → detail → reviewed operation; use header Back, Safari swipe back/forward and refresh a detail URL. Verify no unintended project switch.
- [ ] **Other lanes:** Services → bounded logs, verified private Application links, Jobs → detail → paged output. Long log lines and SHA values should remain readable.
- [ ] **Forms:** create/import, safe GitHub URL syntax, Compose editor, complete applications/tasks JSON review, webhook route confirmation, public SSH key copy. Do not perform destructive edits on production data.
- [ ] **Small viewport:** test 320, 375 and 430 CSS px where available, portrait/landscape, scroll and keyboard focus. No horizontal page overflow, clipped primary actions or undersized touch controls.
- [ ] **Accessibility:** VoiceOver navigation, focus order, control labels, “Skip to content”, error announcements, readable text at 200% zoom/large Dynamic Type, reduced motion. Do not interpret status through color alone.
- [ ] **Controller recovery:** in a disposable environment only, suspend/reconnect browser, test second tab after A→B→A switch, verify stale screens become read-only and unknown POST outcomes do not auto-repeat.
- [ ] **Durable import:** in disposable test data only, reconnect to the same receipt and ensure deliberate retry keeps the same key.
- [ ] **Comparison:** verify the original `/` dashboard and the CLI remain available, no extra services or wider Docker/Web permissions were introduced.

Record any issues with the exact route, browser and reproducible steps in issue #62. A screenshot or physical browser success is user-supplied evidence, not an automated check.

## 3. Published-tag update and rollback (separate gate)

The **real updater can only install a published stable tag**. It is impossible to fully exercise `scripts/updater.py --tag v0.6.0` before the release tag is published. Do not claim otherwise or handcraft a fake “successful release installation”.

After deliberate owner merge/publishing, on a **disposable v0.5.3 installation**:

- [ ] Back up the project registry/worktrees, relevant volumes and `/etc/devstack`; confirm controller is healthy and **inactive** before touching the updater.
- [ ] Verify installed version and CLI; use the existing root-owned stable updater to install `v0.6.0` (never a Git branch). Check its systemd restart/health and release symlink result.
- [ ] Confirm `/__v06`, `/`, strict private access, IPC roles and durable project data/volumes after upgrading. Repeat A→B→A with throwaway projects only.
- [ ] Exercise a **controlled failure/rollback** scenario on disposable infrastructure; verify old pointer/services recover and project data survives. Never inject failures on the production host.
- [ ] Reboot and confirm controller health, single-active invariant and inactive default when appropriate. Verify the CLI `dev` and its explicitly enrolled user still work.

This postpublication test is **required before changing the default root UI or depending on v0.6 for valuable state**. If it fails, keep `/` on the legacy dashboard and ship a new patch after fixing/regression-testing the issue; do not rewrite an immutable tag.
