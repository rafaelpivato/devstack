## PR 02: runtime lifecycle semantics

DevStack runs the dashboard and controller independently of Docker Compose.
The single project can be **inactive**, **activating**, **active**,
**deactivating**, or **error**.

- **Activate:** requires a saved valid Compose file, rejects Docker restart
  policies, clears abandoned project-labelled containers, and performs
  `docker compose up --detach --build --wait`. Only success becomes ACTIVE.
- **Deactivate:** performs Compose down (no `--volumes`) and removes only
  containers bearing the exact Compose project ownership label. When Docker
  cannot verify cleanup, the state is ERROR, never a false INACTIVE.
- **Concurrency:** state is atomically saved before a detached worker begins;
  all transitions, including startup reconciliation, use one host file lock.
  Duplicate activations and stale workers are rejected.
- **Startup:** systemd `ExecStartPre` reconciles to INACTIVE before the
  management UI starts. A controller restart does not silently reactivate
  project containers. If cleanup fails, the UI remains available and shows
  ERROR. Retry deactivation after restoring Docker.
- **Data:** project repositories, Compose YAML, secrets, and named volumes
  remain intact across deactivation/reconciliation.
- **UI/API:** minimal Activate/Deactivate buttons and read-only
  `GET /api/v1/runtime`; CSRF-protected transition endpoints. v0.6 can
  replace the interface without changing lifecycle logic.

**Limit of PR 02:** command workers and standalone image tasks from v0.3
are not yet terminated by deactivation. PR 03 must fence all execution paths,
including delayed jobs and subprocesses, under runtime authorization. Until
then, do not claim unconditional zero project execution while inactive.

**Security boundary:** the Docker daemon is root-equivalent. DevStack only
manages its own Compose-labelled containers, not independent Docker workloads
started outside DevStack.
