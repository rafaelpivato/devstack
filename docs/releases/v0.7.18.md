# DevStack v0.7.18 — branch switching while a project is active

## Repository branch switching

DevStack now allows a **clean, selected repository** in the currently active
project to switch branches without deactivating the runtime or disrupting
unrelated repositories and services. The same reviewed branch-preview/apply
workflow continues to work while all projects are inactive.

The controller reuses the shared source-write lock and active-project ownership
check from repository synchronization (#89). The apply phase rechecks the
preview's opaque revision to reject stale, dirty or changed checkouts, and will
not switch repositories owned by a different active project or mutate sources
during admitted Compose maintenance.

## Configured post-switch service reactions

A successful branch switch creates a controller-owned reaction event for every
explicitly configured restart/redeploy policy (#90) and dispatches the relevant
targeted Compose job. A **preview, no-op, or failed checkout never invokes a
service action**, and the policy default stays **none**. Preview shows each
repository's configured post-switch actions; the reaction/job views track
results separately from the Git checkout result.

Branch event identities are now distinct from Git commit SHAs. Switching back
and forth between the same two branches therefore triggers each opted-in
service reaction, without allowing duplicate actions for an unchanged branch.

The SQLite control registry is upgraded **transactionally from schema v13 to
v14**, preserving prior event receipts and linked job IDs. Earlier supported
schema migrations remain available.

## TrustedOutreach / Beacon Web

From the active TrustedOutreach project, choose **beacon-web** and select
`feature/outreach-revamp` (from `feature/inbox-revamp`). Preview and apply
without deactivating the project.

**Note:** The currently installed Beacon Web configuration has `none` as its
post-update reaction policy for all Compose services. To automatically
redeploy Beacon Web after a branch switch, configure the explicit `beacon-web`
repository → `beacon-web` service reaction as **redeploy** beforehand.
No policy changes are performed by this DevStack release.

## Validation and rollout

CI checks must validate Python unit/integration, Web frontend build, actual
Docker A→B→A, Ubuntu systemd/security and built wheel before publication.

This is the implementation of [issue #126](https://github.com/rafaelpivato/devstack/issues/126).
The branch itself does not change the running project, register a new service,
or publish a release; tag/release deployment remains the separate owner-controlled
main/release workflow.
