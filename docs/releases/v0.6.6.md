# DevStack v0.6.6 — CI-built wheel release, source-only Git

**Do not publish until v0.6.5 is deployed and the standalone updater has been made compatible with mutable wheel releases.** The previously published v0.6.5 updater requires immutable GitHub Releases; a v0.6.5 updater refresh alone does **not** remove that rule. Follow ADR-0006. No GitHub setting change is required.

## Changes

- Stop tracking `src/devstack/static/v06` build output. Vite generates it only inside development builds and GitHub Actions; source archives intentionally **do not contain compiled React files**.
- CI performs a locked frontend installation, complete fail-closed dependency audit, TypeScript/React tests, wheel build and structural/RECORD verification.
- The release job consumes the same-run CI-built `devstack-0.6.6-py3-none-any.whl`, generates a GitHub build-provenance attestation, and publishes a GitHub Release with the wheel and `SHA256SUMS`.
- Only main-only gates can publish; draft assets are checked before publication. Existing partial/mismatched tag/release states fail closed and require operator intervention.
- The root-owned standalone updater downloads only published stable, matching release wheel artifacts, verifies hashes, metadata and bundled frontend assets, and preserves the normal isolated venv, atomic pointer swap, CLI link and rollback.
- The wheel carries a byte-verified copy of the root-owned standalone updater; future versions can explicitly refresh that updater from the selected release's own venv without a Git source checkout.
- No React tooling is required on deployed hosts.

## Deployment order and manual QA

1. Complete the v0.6.5 bridge steps in `docs/releases/v0.6.5.md` on each installed server. Do **not** merge/publish v0.6.6 before the operator checkpoint.
2. No GitHub immutable release setting or personal access token is required. **Before the first mutable wheel release, migrate the existing root-owned updater away from the v0.6.5 `immutable: true` requirement using a reviewed, verified host-updater transition.** The existing v0.6.5 `--refresh-updater` command alone still installs the updater carrying that requirement; merely changing this PR does not fix the deployed updater. Do not merge until a safe operator procedure has been implemented and tested.
3. Back up `/var/lib/devstack`, source workspaces and relevant Compose volumes; confirm no active project and healthy local controller/web.
4. Review and squash-merge the wheel-only PR. Let main-only CI publish and verify it contains exactly the wheel and checksum.
5. Run the existing root-owned updater normally, verify `/opt/devstack/current` now targets v0.6.6 and that React assets load; inspect the private web interface and `dev status`.
6. Exercise deliberate rollback to the known-good v0.6.5 source tag, then re-upgrade, on a disposable host. Check controller IPC/systemd Linux users, Tailscale private surface, saved registry/project state, frontend deep links and A→B→A Docker persistence.
7. Simulate missing/modified wheel, mismatched checksums, partial/draft releases, active runtime, failed service restart, interrupted download and deleted/corrupted manifest. None may destroy data or activate a project.

Wheel checksums alone do not authenticate a publisher independently; GitHub TLS, release metadata/digests and build attestations are the delivery trust boundary. Without release immutability, authorized repository administrators can change an existing release. The stdlib updater does not perform a Sigstore attestation verification on host (ADR-0006). Physical-server acceptance is manual and not implied by passing CI.

No extra GitHub personal access token, Actions secret or immutable setting is required. The workflow uses built-in `GITHUB_TOKEN`, verifies the draft wheel and checksum, and publishes a matching release; it does not overwrite an existing tag or release. A compatible standalone updater accepts either mutable or immutable stable releases, but continues to reject missing/mismatched artifacts.

The `--refresh-updater` command remains a root-only explicit operation after v0.6.6. It validates the selected release venv before reading the embedded updater and preserves its original on-disk backup; no automatic privileged updater replacement occurs.
