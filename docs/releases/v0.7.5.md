# DevStack v0.7.5 — release rollback/false-success hotfix

## Field evidence
On 2026-10-28 a v0.7.3 workstation reported an attempted update to
published v0.7.4, but still showed v0.7.3. A 30-minute Web snapshot recorded
updater-started and updater-exited about 0.13 seconds apart and systemd
success/exit 0. This does not prove a new rollback in that specific attempt:
an earlier failed-v0.7.4 marker can cause an immediate **successful skip**
without running the release installation.

## Fix
- Previous failed-release marker is now a nonzero result, never a successful
  no-op. Keep markers protected: do not auto-clear/retry a known failed tag.
- Old postinstall hook had only a 25-second timeout, but synchronously waited
  for systemd and Tailscale reconciliation. The wheel-owned hook now installs
  fixed systemd units and queues only bounded no-block service refreshes;
  existing root network-reconcile.timer performs Tailscale work with retries.
- Queue a restart of an already-running `devstack-public` process on each new
  wheel activation, even when Funnel preferences are unchanged; old anonymous
  MCP code must not remain the process handling requests.
- Versioned updater for subsequent upgrades allows a 120s hook budget, while
  this v0.7.5 hook remains compatible with deployed older 25s updaters.
- Report updater-failed on a nonzero systemd result; never reveal raw host logs.

## Recovery/acceptance
Use Administration → Published updates, after v0.7.5 is released, rather than
retrying the known-failed v0.7.4. Check that the private dashboard reopens on
:8443, installed version changes to v0.7.5, controller remains healthy and
the public MCP reconnects via OAuth while enabled; :443 webhooks remain
unchanged. If it fails, copy 30-minute diagnostics. No routine SSH.

The exact first failure on the field server is unconfirmed; a live upgrade
and stored marker state still require operator-controlled evidence.
