# DevStack v0.6.0 — Project-first mobile interface

**Release candidate only.** This document is prepared for the owner-controlled `integration/v060-ui` → `main` review. No tag or published release exists until owner approval and main-only release CI succeeds.

## What's new

- **One active project, immediately visible.** The new React/TypeScript mobile interface opens the active project's workspace, or a deliberate project chooser when nothing is active. Browsing another project never activates it.
- **Predictable navigation on a phone.** Project → Repositories, Services, Applications, Jobs or Configuration → details, output or reviewed actions. Native browser history, deep-link reload and parent-aware Back. Neutral charcoal UI with restrained accents, explicit state text, high-contrast focus and touch-friendly controls.
- **Projects and GitHub imports.** Create an empty project, import a GitHub repository and revisit controller-durable import receipts. Long mutations survive browser disconnects; unknown outcomes never trigger automatic duplicate submits.
- **Existing controller operations, new screens.** Reviewed runtime activation/switch/deactivation/recovery, repository status/update/branch and configuration source review, bounded Compose service logs, verified Tailscale-only application links, supervised tasks/jobs with paged logs and independent cancellation.
- **Safer settings.** Compose YAML revision checks; full applications/tasks collection replacement now includes controller-owned atomic revision validation to reject stale edits. Webhook routing, project rename, GitHub public SSH identity and the stable-release updater live in their appropriate project or global administration screens.
- **Build and release security.** The generated frontend assets are versioned in the Python wheel and require no Node runtime on the server. Typechecking, tests, reproducible assets, wheel inclusion, and the **full npm dependency audit** are mandatory; the main-only publisher gates on them as well as Docker A→B→A and Ubuntu systemd/IPC permissions.

## Preview and cutover

The v0.6 UI is staged at **`/__v06`** on the private dashboard host. **The existing v0.5.3-compatible dashboard remains at `/` in this candidate.** This is deliberate: a physical iPhone accessibility/navigation review and a disposable Ubuntu installation/update/rollback test must be recorded **before deciding to make v0.6 the default root UI**. A successful CI run alone is not that approval.

Real iPhone Safari/VoiceOver, 320–430px layouts and text scaling, cross-tab runtime/reconnection, unknown-operation recovery, and physical-host update/rollback are still **pending**, documented in [v0.6 UX acceptance](../v0.6-ux-parity-audit.md). Do not present them as completed.

## Installation and upgrade

For a **new clean Ubuntu host**, the existing [trusted installer](../../scripts/install.sh) installs the latest **published** stable GitHub release; it rejects old v0.5.1 singleton state. Do not install an unreviewed integration branch through the production installer.

For an existing v0.5.3 installation, deactivate the single active runtime before using the restricted released-version updater. The updater clones the published version tag, builds an isolated Python venv and switches the release pointer only after health checks; failure attempts to roll back. Preserve backups of repository worktrees, SQLite state and Docker volumes. Do not expect an in-place upgrade of v0.5.1 to work.

The native `dev` CLI and its `devstackipc` group enrollment remain supported and use the same controller IPC as the dashboard; no broad Docker access is granted to the web service.

## Scope and limitations

No browser terminal, arbitrary shell, automatic GitHub pull/rebuild, editable deployment IDE, public controller API, GPT connector or usage telemetry was introduced. The before-v1.0 repository synchronization and future read-only observability ideas stay on their own roadmap.

This release must not be tagged by a feature PR. The owner explicitly reviews the final draft release PR, and only a merge to `main` runs the versioned publisher. Subsequent changes to a published immutable tag require a new release number.
