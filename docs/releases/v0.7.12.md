# DevStack v0.7.12 — fix #116: Funnel readiness on working server

The v0.7.11 preflight used `tailscale_layout.identify()`, a historical
path-oriented route layout. The **current** reconciler uses a single public
HTTPS :443 **root proxy** to loopback :8768 and private dashboard HTTPS
:8443, described by `networking.classify()`. Consequently a healthy
authenticated MCP server reported both routes as `unknown`.

The preflight now reuses `networking.classify()`, preserving the **same
strict exact-match policy** that protects the reconciler. No Tailscale route
is changed or any public access widened.

For additional observability, a small enumerated `network_preflight.reason`
field differentiates `routes_unrecognized` from
`serve_status_unavailable` and `public_route_pending`. The local gateway
HTTP health check is independent of route classification, so a working
loopback service can be reported even when a route is unrecognized. An
externally reachable ChatGPT session still requires a successful real MCP
call; the local preflight never claims to test external TLS.

All results continue through the existing root collector, bounded JSON
snapshot, private Web diagnostics and controller IPC to authenticated
`devstack_diagnostics`. No raw CLI output, machine identity, hostnames,
token, or route map is published.

Validation includes the current :443 root proxy with MCP only and
MCP+webhooks, public-disabled and pending states, old-layout rejection,
identity mismatch, stale snapshots and secret filtering. Existing Ubuntu
systemd, Docker integration and frontend checks remain required.

After owner merges/deploys, query `devstack_diagnostics(minutes=5)`.
Expected for the existing connected server:
`health=ready`, `tailscale=connected`, `identity=verified`,
`private_dashboard=ready`, `public_funnel=configured`,
`gateway=ready`, `reason=none`.
