# DevStack v0.6.8 — targeted Compose reactions (#90)

This release builds on v0.6.7's active-project Git synchronization. Source
updates no longer require a project deactivation; service actions are separately
controlled and default to **None**.

## Changes

- Per-repository **None / Restart / Redeploy** settings mapped to explicitly
  selected Compose services. An actual fast-forward while the project remains
  active records a targeted reaction; read-only checks and unchanged HEAD
  never start Compose. Multiple repository updates for the same service can
  be coalesced into one supervised job.
- **Manual Restart / Redeploy** actions for one Compose service in Services,
  regardless of Git policy. Restart uses the current container/image; Redeploy
  runs targeted Compose `up --build --force-recreate --no-deps` with wait.
- Controller-only Docker authority; active project/generation fencing; shared
  bounded job logs; stable service names; explicit, non-replayed interruption
  receipts. No host shell or separate background daemon.
- SQLite v11→v12 migration preserves all existing data and defaults every
  repository/service association to no automatic reaction.
- Existing whole-project Compose Build/Restart remains available in Jobs.

## Upgrade

Merging the release candidate to `main` initiates the immutable verified
wheel release workflow. Deactivate the active project before updating
**DevStack itself**. Back up `/var/lib/devstack`, source worktrees and
Compose volumes. Install the published `v0.6.8` wheel through the existing
independent updater; do not install GitHub source archives. Activation after
upgrade retains registered project/repository data.

## Optional manual acceptance

1. Enable Redeploy for only one service under a repository, then push and
   fast-forward its tracked branch. Confirm one job runs, the target service's
   container ID changes, and other services retain theirs.
2. Set None and repeat a Git update: source advances without Docker actions.
3. Manually Restart and Redeploy a selected service from Services. Confirm
   bounded logs and job status. Review behavior when the project is inactive
   or another project is active.
4. Simulate build failure or project switch and review retained error/skip
   receipts. Do not interpret CI as a substitute for real-host acceptance.

Enable policies only for services you are comfortable updating unattended.
There is no automatic rollback of unsuccessful container deployments.
