# DevStack v0.7.14 — automatic recovery after a Tailscale hostname change

## Fix

v0.7.13 can rename the Tailscale device while the node-level Serve/Funnel
configuration still references the previous MagicDNS FQDN. The existing
reconciler then rejects the stale configuration, and the private HTTPS :8443
dashboard and public MCP :443 can be unavailable.

v0.7.14 repairs this **without renaming the device back**, additional
services, SSH as a routine prerequisite, custom proxies, Docker changes or
re-enrolling in Tailscale. The established root-owned
`devstack-network-reconcile.timer` checks the current node ID/tailnet pin
and the exact legacy/current Serve/Funnel port maps. If and only if it finds
one fully managed, unambiguous **current v0.7.13** map with a different
machine label in the same tailnet, it atomically rebinds the private Serve
:8443 and optional public Funnel :443 to the currently assigned FQDN.

Tailscale currently exposes no documented node-level config editing via
`serve set-config`, which edits Services only. This hotfix uses the
existing `tailscale serve set-raw` node-level operation with a **fixed
argv**, generated and strictly allowlisted payload, and pinned identity
checks before and after. The command is only called on the verified
hostname-rename mismatch. It never runs `serve reset`, `funnel reset`,
`tailscale up`, `tailscale logout` or arbitrary host commands, and
never publishes the private :8443 management target. Any unknown, mixed,
foreign, or unexpected configuration fails closed.

Reconciliation runs on the already installed root-owned systemd timer
outside the upgrade's short postinstall hook. The existing v0.7.13
standalone updater checks its local controller/web health on
`127.0.0.1:8765`, so a broken Tailscale HTTPS entrypoint does not itself
block installation of this patch. It **still requires an inactive project
runtime** and will not interrupt a running project merely to upgrade.

Tailscale Serve provisions a new HTTPS certificate automatically once the
rebound endpoint is active. DNS propagation, public Funnel DNS publication
and certificate issuance depend on Tailscale and may take additional time.
The hotfix checks the exact *local* Serve/Funnel state but does not claim to
verify external TLS or ChatGPT reachability.

## Recovery

1. If the automatic stable-release updater is enabled and the project is
   inactive, it checks for new releases roughly every 30–35 minutes.
2. Once v0.7.14 is installed, the existing root network timer retries the
   safe rebind automatically (normally within three minutes).
3. Reopen the current URL:
   `https://devstack.turkey-shiner.ts.net:8443/`.
   The public MCP URL, if enabled, is
   `https://devstack.turkey-shiner.ts.net/mcp`.
4. Confirm the certificate status in Tailscale → Machines and inspect
   Administration → DevStack diagnostics (1/5/30 min) for sanitized
   `mcp-hostname-rebind-*` events if the dashboard becomes available.

If the updater is blocked by an active project or unhealthy *local*
controller, the existing Web-first policy permits SSH as an **exceptional
recovery path**. From an owner-controlled Ubuntu shell, inspect the
installed version and the bounded systemd journal before manually
initiating the existing trusted updater; do not reset Tailscale routes or
re-enroll the node. Upgrader rejection of an active project must be
resolved deliberately, not bypassed.

## Validation

Regressions cover private-only and opt-in public mappings, no-op healthy
state, tailnet/identity mismatches, accidental public :8443 disclosure,
unknown handlers/mixed hostnames, preferences conflict, concurrent
edits, CLI timeout/failure, incomplete readback, and automatic timer
recovery without requiring the Web dashboard.
