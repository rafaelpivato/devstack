# DevStack v0.6.7 — active-project repository synchronization (#89)

This patch release packages the merged implementation of [#89](https://github.com/rafaelpivato/devstack/issues/89). It changes repository synchronization, **not** application/container restart policy (#90).

## Changes

- **Update checked-out Git code while its own project is active:** run a safe fast-forward update for one repository or the project's existing durable batch. No project deactivation/reactivation, implicit Compose down/up, service restart/rebuild, or activation-generation change is requested by repository sync. A different active project and runtime transitions remain write-protected.
- **Optional per-repository policy:** `manual` (default), `check` (periodic remote fetch/status only), or `update` (opt-in automatic fast-forward). The existing controller runs bounded polling approximately every five minutes; no webhook, domain, or separate daemon is required.
- **Safety and visibility:** require a tracking branch and clean worktree, preserve an expected HEAD and fast-forward-only merge, serialize with runtime transitions, and record bounded check/update receipts and errors. Interrupted or ambiguous updates pause automatic retries until manual intervention.
- **Interfaces:** project repository UI controls and status, protected HTTP/controller IPC, and SSH `dev repo check` / `dev repo sync-policy` commands.
- **Persistence:** SQLite schema v10→v11 adds synchronization policy and receipts while retaining existing project and runtime data.

Repository file changes alone do not reload application processes or rebuild images. Targeted per-application reactions are tracked separately in [#90](https://github.com/rafaelpivato/devstack/issues/90).

## Release and upgrade

- Merging the version-bump PR to `main` automatically invokes the guarded release workflow. It requires matching `pyproject.toml`, frontend package/lockfile versions and these notes, verifies the wheel and checksums, and publishes the `v0.6.7` GitHub Release only after required checks succeed. The release must contain `devstack-0.6.7-py3-none-any.whl` and `SHA256SUMS`.
- For deployments older than v0.6.6, first complete the v0.6.5→v0.6.6 updater compatibility migration in [v0.6.6 notes](v0.6.6.md) and [ADR-0006](../adr/0006-ci-release-artifacts.md). Do not install from the GitHub source archive; v0.6.6+ uses CI-built wheels.
- Back up `/var/lib/devstack`, registered repository worktrees and relevant Compose volumes. **Deactivate the active project before upgrading DevStack itself**, since the root-owned standalone updater still requires an inactive healthy controller. This is distinct from the new ability to update a project's Git checkout while that project stays active.
- On a supported v0.6.6 installation, install the published release with `sudo python3 /usr/local/lib/devstack/updater.py --tag v0.6.7`. Confirm `/opt/devstack/current`, the dashboard, `dev status`, the upgraded schema and preserved project configuration before activating a project again.

## Live acceptance still required

CI covers unit, frontend/package integrity, Docker Compose smoke, and fresh Ubuntu systemd/Unix-socket permissions. **It does not replace acceptance on the actual Ubuntu server.**

1. With one project active, record its activation generation, container IDs and repository HEAD. Push a new commit to the remote tracking branch, click **Check remote now**, then manually update the repo. Confirm files and HEAD advance but the project remains active and the generation/container IDs are unchanged.
2. Verify per-repository `check` and `update` policies after opting in, including recorded check/update outcomes and a clean return to `manual`.
3. Confirm dirty or untracked worktrees, divergence, missing upstream, foreign active project, interruption and transition races fail safely and do not mutate another project's checkout.
4. Confirm there was no Compose stop/recreate/rebuild, no implicit application reload, no data loss, and no unexpected configuration import. Verify normal project deactivation/reactivation remains functional.

Keep [#89](https://github.com/rafaelpivato/devstack/issues/89) open until the live acceptance results are recorded. Do not conflate release CI success with physical-host validation.
