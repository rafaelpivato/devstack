# v0.5 PR 03 — Execution isolation

The single lifecycle controller owns admission and shutdown for DevStack
managed runtime operations. UI routes only queue work; detached workers
**recheck active admission immediately before Docker execution**, under a
process-shared file lock.

**Allowed while inactive:** repository configuration, Compose definition
editing/validation, viewing logs and metadata, Git operations, and DevStack
management itself. **Disallowed:** Compose build/restart/up/down except via
the runtime transition controller, Compose exec/run, standalone Docker images,
and saved executable tasks. Legacy systemd/Compose service execution is
disabled; legacy services are rejected in the v0.5 workspace schema.

When deactivation begins, it changes the persistent phase before launching
its worker. Running workers observe the phase change, terminate their Docker
CLI and named ephemeral containers, and mark their results. Pending jobs are
invalidated, including stale jobs from earlier boot IDs. Deactivation waits
for both worker types; it removes only Compose-owned or exactly DevStack-labelled
containers and preserves named volumes. A failure to stop workers or remove
owned containers results in **ERROR**, not a false INACTIVE.

A queued job cannot be replayed after reactivation: its record is checked
again under the same lifecycle lock at the point of execution. Unrelated
Docker projects are not managed.

**Scope:** This guarantees DevStack-managed project execution when inactive.
The webhook receiver will be gated in PR 04; direct root/host commands and
containers created outside DevStack cannot be controlled by this service.
