# DevStack v0.5 — fresh Ubuntu installation and release safety

**Status:** PR 06 prepares the implementation; `v0.5.0` must not be
published until PR 07 merges after all checks pass.

## What is supported

- A **new** Ubuntu 24.04 LTS (or later with Python 3.11+) host on any provider:
  AWS, Google Cloud, DigitalOcean, Linode/Akamai, local virtualization, etc.
- A single Linux user `devstack` and one independently managed project
  workspace in `~devstack/.config/devstack/workspace.toml`.
- Docker Compose for the project, systemd for the host controller,
  Tailscale for optional private device access, and an opt-in webhook Funnel.
- State starts **INACTIVE** after host boot/restart reconciliation, without
  removing project repositories or Docker named volumes.
- No migration of v0.4 `projects.toml`, old service configuration, or Docker
  resources. Provision a fresh machine; do **not** point v0.5 at existing
  v0.4 project directories.

## One-line installation after the v0.5.0 release

Review the published installer first, then execute it with root privileges.
Both the downloaded installer **and all helper scripts/systemd units/packages
it installs** use the same published release tag:

```bash
curl -fsSL https://raw.githubusercontent.com/rafaelpivato/devstack/v0.5.0/scripts/install.sh \
  | sudo env DEVSTACK_RELEASE_TAG=v0.5.0 bash
```

This is provider-independent. On a new Ubuntu cloud-init instance, the
same command can be put in a root-run `#!/bin/bash` user-data script, with
`set -euo pipefail` first. Nothing requires AWS services/credentials or a
persistent deploy key for the public DevStack repository.

The installer can instead query GitHub's latest **stable** release when
`DEVSTACK_RELEASE_TAG` is omitted. It rejects releases older than v0.5.0,
malformed tags, and existing v0.4 `projects.toml`. It downloads verified
paths from `raw.githubusercontent.com/<owner>/<repo>/<tag>/...`, not
`main`, then explicitly installs that *same tag* before enabling timers.
The updater confirms that the Git tag matches the package version in
`pyproject.toml`.

Onboard Tailscale with the installer-provided interactive script, or the
existing opt-in browser flow. No default public dashboard, host web terminal,
webhook Funnel, or application port is published. Ports are set by the
project's own Compose file and should bind to the server's exact Tailscale IP.

## Release compatibility and old-host warnings

v0.5 is **not** a compatible update for v0.4. The old updater follows the
latest stable GitHub release, and we cannot patch installed copies on
already-running old machines retroactively.

When a v0.4 updater downloads v0.5, the candidate application invokes the
`devstack.compat_guard` before binding the management or webhook listener.
A v0.4 `projects.toml` or `DEVSTACK_CONFIG` pointing to that legacy format
causes candidate startup/health checks to fail. The independent old updater
should then restore its previous release pointer. **This is a fallback,
not a guarantee of uninterrupted availability**: the old updater may
temporarily restart the service and report v0.5 as failed.

**Before publishing v0.5**, operators keeping their v0.4 machines must
manually disable automatic upgrades:

```bash
sudo systemctl disable --now devstack-update.timer
sudo systemctl stop devstack-update-request.path
```

These commands are for existing v0.4 hosts only. They do not migrate or
delete any project files. No code in PR 06 can automatically disable an old
updater on a machine where it is not yet installed.

On new v0.5 hosts, the updater avoids crossing to another minor release
line (such as the intentionally incompatible v0.6) automatically. Review and
explicitly select a future major/breaking release after any required
migration or fresh provisioning.

## Acceptance checks before the v0.5.0 publication

1. `python -m unittest discover -s tests -v`, including compatibility,
   updater policy, API and lifecycle/worker cancellation tests.
2. `bash -n scripts/install.sh` and distro-neutral source/unit checks.
3. Build and inspect an actual wheel to ensure packaged templates, CSS, and
   JS are present; start the **installed** Gunicorn WSGI app from an
   unprovisioned home and check `/healthz`, `/api/v1/dashboard` and assets.
4. Simulate an old v0.4 host and confirm the candidate WSGI fails before
   binding, so an older independent updater can roll back.
5. Real Docker integration: Compose activation/deactivation, private
   webhook forwarding while ACTIVE only, standalone image job shutdown,
   and preservation of Docker named volumes.
6. Before release PR 07, check that no v0.4 server will be knowingly
   subjected to unintended automatic release adoption.
7. Merge the release PR, then perform a **real fresh Ubuntu 24.04 VM
   installation** using the published tag. The mocked/CI tests here
   cannot claim to have completed that real host provisioning step.

Package version stays `0.4.0` throughout PR 06. PR 07 alone bumps
`pyproject.toml` to `0.5.0` and triggers the publishing workflow.
