# v0.5.2 Stage 5H — selective Git template sync

**Unreleased integration work; fresh Ubuntu / SQLite schema v6 only.**

This completes the native v2 **review → selective apply** control flow. It
does not import or depend on legacy singleton `project_sync.py`.

## Behavior

1. A project-bound GET review compares the registered Git `.devstack/`
   definitions with its private import baseline and authoritative managed
   configuration. It presents named application, task and Compose changes,
   local-customization flags, and a SHA-256 revision of all review inputs.
2. The owner selects explicit change IDs. An existing definition whose local
   contents have diverged from the baseline requires its own explicit overwrite
   checkbox. Upstream deletions cannot be selected for automatic deletion.
3. A controller-only `source_apply` IPC operation validates identity, revision,
   requested changes, overwrite approvals and the runtime-inactive/clean-Docker
   requirement under the same global coordinator lock as activation.
   A stale revision refuses application. Compose changes pass Docker Compose
   configuration validation before any database change.
4. SQLite application/task updates and a **frozen, allowlisted file-publication
   journal** commit in the same SQLite transaction. The journal contains only
   targeted `managed/` and `baseline/` snapshots. File updates use
   controller-owned atomic rename and fsync. Successful publication deletes
   the journal.
5. A crash after the SQL commit but during file publication retains the
   journal. The controller refuses normal operations and activation until
   runtime reconciliation verifies no owned containers, then idempotently
   replays the frozen snapshots. Startup and explicit reconciliation use the
   same guarded repair. Failure remains closed and operator-retryable.

The baseline advances **only for individually applied changes**; untouched
upstream changes remain pending for a later review. Git checkouts and other
projects never change. No webhook or command can apply templates.

## Storage and failure model

`source_sync_pending` stores one in-flight operation per project. It is
created along with authoritative SQLite edits; an incomplete publication
is visible as an explicit barrier rather than silent partial success. An
interruption *before* the SQLite transaction commits makes no changes;
an interruption *after* commit rolls forward from the exact frozen intent,
without revisiting Git or accepting a new review. If a destination is unsafe
or unavailable, the journal remains pending and recovery refuses admission.

File snapshots, imported baselines and DB are not represented as a single
filesystem atomic transaction; the durable journal is the recovery boundary.
The sync never deletes checkout files or named volumes.

## API

- `GET /api/v2/projects/<project-uuid>/source-review`
- `POST /api/v2/projects/<project-uuid>/source-review/apply`

POST JSON shape:

```json
{
  "revision": "<SHA-256 from review>",
  "selected": ["application:API", "task:tests", "compose.yaml"],
  "overwrites": ["application:API"]
}
```

The `overwrites` list must match exactly the selected entries flagged as
locally customized; there is no all-overwrites switch. The browser provides
the same explicit controls via CSRF-protected form.
